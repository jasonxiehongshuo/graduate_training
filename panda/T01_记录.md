### 1.1 版本兼容性坑（重要教训）

robosuite 1.4.1 的元数据只写 `mujoco>=2.3.0`，pip 在 2026 年会把 `mujoco 3.16.0` 装进来，导致两处崩溃：

- `binding_utils.py`：`assert joint_type in (mjtJoint.mjJNT_HINGE, ...)` → AssertionError
  （mujoco 3.x 的 `mjtJoint` 改为 pybind11 enum，与 numpy int 的 `in` 比较失效）
- `base_controller.py`：`mujoco.mj_fullM(..., self.sim.data.qM)` → AttributeError
  （mujoco 3.x 移除了 `MjData.qM`）

**修复**：卸载 mujoco 3.16.0，改装 mujoco 2.3.7。修复后官方示例可完整运行。
**结论**：robosuite 1.4.1 必须配 mujoco 2.x；若要用 mujoco 3.x，须同步升级 robosuite 至 1.5.1+。

### `action`

- controller: JOINT_VELOCITY（default_panda.json）
- 输入 [-1,1] 映射到关节速度 [-0.5, 0.5] rad/s
- robot.dof = 8（臂 7 + 夹爪 1），action_dim = 8
- 夹爪 dof=1，两指为 mimic 联动

### `reward`
- 实测（horizon=100，随机策略，seed=0）：
  - 稀疏 `reward_shaping=False`：非零 0/100，累计 0.0000，单步范围 [0, 0]
  - 稠密 `reward_shaping=True`：非零 100/100，累计 0.8432，单步范围 [0.0044, 0.0112]
- 由稠密单步 0.0112 反推：1 - tanh(10·d) = 0.011 → d ≈ 0.29 m，
  说明随机策略的夹爪始终在方块 30cm 外，从未接近
```
reward = 0.0 #初始化奖励

        # 完成抓取动作成功的奖励
        if self._check_success():
            reward = 2.25

        # 使用塑性奖励
        elif self.reward_shaping:

            # 接触奖励
            cube_pos = self.sim.data.body_xpos[self.cube_body_id] #方块刚体的坐标
            #机器人末端执行器的坐标
            gripper_site_pos = self.sim.data.site_xpos[self.robots[0].eef_site_id]
            #计算欧氏距离
            dist = np.linalg.norm(gripper_site_pos - cube_pos)
            reaching_reward = 1 - np.tanh(10.0 * dist)
            reward += reaching_reward

            # 抓取奖励
            if self._check_grasp(gripper=self.robots[0].gripper, object_geoms=self.cube):
                reward += 0.25

        # 奖励缩放，以成功奖励为基准，进行缩放/ 2.25
        if self.reward_scale is not None:
            reward *= self.reward_scale / 2.25

        return reward
```
### `done` 
> `grep -rn "self.done = " ~/miniconda3/envs/panda/lib/python3.10/site-packages/robosuite/environments/`  
> 位置base.py:432  
> self.done = (self.timestep >= self.horizon) and not self.ignore_done  

- done 判据：`(timestep >= horizon) and not ignore_done`（base.py:432）
- timestep 在 step() 开头自增，故 horizon=30 时第 30 个动作返回 done=True
- 用 `>=` 而非 `==`：容错，防止 timestep 越过 horizon
- 不含 success 判定：Lift 是固定长度回合，成功与终止解耦
- ignore_done=True 时 horizon 失效（demo_device_control 即此设置）
```
import numpy as np
import robosuite as suite

env = suite.make("Lift", robots="Panda", has_renderer=False,
                 has_offscreen_renderer=False, use_camera_obs=False,
                 horizon=30, hard_reset=False)
env.reset()
for t in range(35):
    obs, r, d, info = env.step(np.zeros(env.action_dim))
    if env.timestep == 1:
        print(f"1 个动作 = {int(env.control_timestep/env.model_timestep)} 次物理积分 "
              f"(control_timestep={env.control_timestep}s, model_timestep={env.model_timestep}s)")
    if d:
        print(f"done=True 于第 {t+1} 个动作, timestep={env.timestep}, horizon={env.horizon}, cur_time={env.cur_time:.2f}s")
        break
try:
    env.step(np.zeros(env.action_dim))
except ValueError as e:
    print(f"done 后 step -> ValueError: {e}")
env.close()
```

### reset 实测
- cube_pos 三次不同：x/y 由 UniformRandomSampler 在 ±0.03 采样，z 恒为 0.8309
- eef_pos 三次不同（-0.1107 / -0.1053 / -0.1002）：initialization_noise="default"
  给关节初始位姿加了噪声，改为 None 可固定
- 计数器复位：timestep=0, cur_time=0, done=False
- hard_reset=True 二次 reset 703ms vs False 0.8ms，差 ~900 倍，
  sim 对象被重建=True；训练循环必须用 False
- seed 控制有效：np.random.seed(0) 两次 cube_pos 完全一致，seed=1 与 seed=0 不同
- deterministic_reset=True 失败：跳过 sample() 后方块停在 qpos=0，
  cube_pos=[0,0,0] 落在桌面下方，该实验无效 → 属已知失败，保留记录
- 边界：z=0.8309 距判据 0.84 仅 1cm，说明判据只看高度不看是否夹持

### 实验 B：控制参数（唯一变量 = control_freq）
| freq(Hz) | 每步仿真时长(s) | 20步总时长(s) | dz(m) |
|---|---|---|---|
| 10 | 0.1000 | 2.00 | 0.0372 |
| 20 | 0.0500 | 1.00 | 0.0056 |
| 40 | 0.0250 | 0.50 | 0.0004 |

**实验 B 是非线性的，这一点必须说清**：

总时长比为 4 : 2 : 1，位移比却是 93 : 14 : 1，衰减远快于线性。原因两条且相互耦合：

1. **单步内积分次数不同**：`step()` 内层跑 `int(control_timestep / model_timestep)` 次。
   10Hz 时 50 次、20Hz 时 25 次、40Hz 时 12 次。
2. **目标速度更新频率不同**：`JOINT_VELOCITY` 每步重新设定目标速度；40Hz 下每个目标只
   维持 25ms，关节还没加速就被下一次目标覆盖。

所以 `control_freq` 改的不只是时间尺度，还改变了**控制带宽**。不能把它当成单纯的快慢调节。

### 结论
- A：reset 通过 `placement_initializer.sample()` 决定方块位姿，可复现、可控；
  三组 eef 标准差均为 0，证明 `initialization_noise=None` 使机器人起始位姿受控
- B：`control_freq` 同时改变积分次数与目标更新频率，位移衰减呈非线性（93:14:1）
- 两项均为单变量对照，其余条件固定
- 边界：均未改变任务难度，随机策略仍无法完成 Lift

### 失败解释

**现象**：随机策略 5 回合 `max cube_z` 始终低于 0.84，Lift 从未成功；稀疏奖励全程 0。

**归因**：动作由 `np.random.uniform(-1,1,8)` 采样，无目标导向，夹爪从未在方块两侧闭合。
由稠密奖励反推，夹爪与方块距离始终约 0.29m，机械臂整体没靠近过目标。

**对照**：同环境下用 `demo_device_control` 键盘遥操作可完成抬升，说明环境、物理、
成功判据均正常，失败纯粹来自策略。

**边界**：这不能说明环境有问题，也不能说明 Lift 困难；只证明"无目标导向的随机动作
不可能完成任务"。这正是 T03 状态机、T04 BC、T05 PPO 要解决的问题。

## 5. 必要知识小结

- **MuJoCo**：物理引擎。模型（XML）定义刚体/关节/执行器，数据（`MjData`）存
  `qpos`/`qvel`/`ctrl`。一次 `sim.step()` 推进 `model_timestep=0.002s`。
- **关节状态**：7 个臂关节的角度与角速度；观测里角度用 cos/sin 编码，避免 ±π 跳变。
- **控制输入**：`env.step(action)` 的 8 维经 `JOINT_VELOCITY` 映射为关节目标速度
  （±0.5 rad/s），引擎内部积分 25 次（0.05s ÷ 0.002s）。
- **动作空间**：连续，`[-1,1]^8`，7 关节速度 + 1 夹爪。
- **回合**：从 reset 到 done。done 仅由 `timestep >= horizon` 触发（固定长度），
  与任务成功无关；成功由 `_check_success` 单独判定（`cube z > 0.84`）。
